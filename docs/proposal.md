# moonfs 项目申报书

## 基本信息

- 项目名称：moonfs —— 纯 MoonBit 的只读文件系统镜像解析库（NTFS / ext4）
- 参赛者：王文挺
- 联系方式：见报名问卷（公开仓库不放置个人手机号）
- GitHub 仓库：https://github.com/wwt1733/moonfs
- 项目方向：存储基础设施 / 文件系统解析
- 项目性质：原创实现（依据公开规范编写，非移植）

## 项目简介

moonfs 用纯 MoonBit 实现磁盘镜像上的文件系统解析，直接读取镜像字节，不挂载、不依赖任何 C 库。

目标用户是需要在非特权环境里访问镜像内容的人：在浏览器里分析用户上传的镜像、在 CI 里检查构建产出的根文件系统、在取证工作站上批量扫描上百块磁盘，或者在一个没有 root 的容器里做数据提取。

## 项目价值与生态定位

**痛点**：现在能解析 NTFS 的实现几乎都是 C 库——Linux 侧是 `ntfs-3g` 和内核 ext4 驱动，Windows 侧是 `libfsntfs`。它们要么需要挂载（要求 root 或管理员权限），要么必须链接原生 ABI。结果是：**在 WebAssembly 里没办法读一块磁盘镜像**。不是没人想做，是现有实现的形态决定了它们进不了 wasm。

**生态位**：MoonBit 的 `preferred_target` 可以是 wasm，而 wasm 里没有 FFI 可用的 C 库。moonfs 补的正是这个位置——一份不依赖原生 ABI 的文件系统解析实现，能在 native / js / wasm / wasm-gc 四个后端上跑同一份代码。这不是"把 C 库翻译一遍"，而是只有在纯 MoonBit 前提下才成立的能力。

**与已有项目的关系**：我查过 mooncakes.io 全部 3794 个包，`ntfs` 与 `ext4` 相关实现数为 **0**。FAT 家族已有 `chenliyi-cly/moonfat`，因此本项目**不做 FAT**，后续通过统一的卷接口对接它，避免重复建设。

## 预期使用场景

1. **浏览器端镜像浏览（核心场景）**：用户在网页上传一块 `.img`，前端直接用 moonfs（wasm-gc 后端）列出分区、目录与文件内容，全程不上传服务器。现有 C 绑定方案在此场景不可行。
2. **数字取证**：打开 DD / E01 镜像，枚举卷上的文件并导出 MFT 时间戳做时间线，不需要挂载、不需要写权限，可以在只读介质上批量跑。
3. **CI 中的镜像内容校验**：构建完根文件系统镜像后，直接断言镜像里没有多余的调试文件、`/etc/shadow` 的权限位正确、关键二进制存在——不需要起容器、不需要挂载 loop 设备。
4. **教学与结构可视化**：把 MFT 记录、属性、runlist、extent tree 逐层打印出来，用于讲解文件系统内部结构。

## 拟实现的核心功能

一期（只读）：

- 卷定位：MBR 与 GPT 分区表解析，含 GPT 头与分区项数组的 CRC 校验
- NTFS：卷头几何、MFT 记录与属性解析、常驻/非常驻数据读取、`$I30` 目录索引遍历、路径查找与文件内容导出
- ext4：超级块、块组描述符、inode、extent tree、目录项遍历与文件读取
- 统一接口：一个卷抽象，使 NTFS / ext4 / 后续的 FAT 能被同一套 CLI 与上层代码调用
- CLI：`info` / `partitions` / `ls` / `cat`

## 明确不做的事

边界比功能列表更重要，写在这里避免交付时扯皮：

- **只读**。不写镜像、不做日志重放（NTFS `$LogFile`、ext4 journal）。
- **不做 NTFS 压缩属性与 EFS 解密**。遇到时返回 `Unsupported`，绝不返回解错的字节。
- **不做 ext4 htree 哈希目录的查找语义**。目录遍历走线性扫描，慢但正确。
- **不做删除文件恢复**。

## 实现路径与技术理解

解析分三层，每层都能独立测试：

1. **字节层**（已完成）：定长整数读取，每次读取前校验 `[offset, offset+n)` 是否落在缓冲区内。这一层看着琐碎，但它是后面所有判断的基础——镜像截断时必须在第一层就报错，否则上层会把残缺结构解析成看起来合法的数据。
2. **定位层**（已完成）：分区表 → 卷起始偏移 → 卷头几何。NTFS 的难点是 `clusters_per_mft_record` 是**有符号**字节，值为负时表示 `2^-n` 字节而非负数个簇；这一点错了，后面读 MFT 全部跑偏。GPT 则必须先验 CRC 再用偏移，因为 CRC 不过的头部字段可能指向镜像任意位置。
3. **结构层**（进行中）：MFT 记录 → 属性 → runlist → 数据。NTFS 的数据是**非连续**的，`$DATA` 属性里存的是 `(长度, LCN 增量)` 变长序列，必须解码成区间表才能读文件；文件名在 `$FILE_NAME` 属性里，大目录要被索引项分散到多个 `$INDEX_ALLOCATION` 块中。

**验证方式**：不靠"看起来对"。用 `mkfs.ntfs` / `mkfs.ext4` 生成已知内容的镜像，逐字段断言元数据；同一批镜像再用 `7z l` 与 `debugfs` 导出目录树，逐条比对；三个后端（native / js / wasm-gc）跑同一套测试，任何后端不一致即视为失败。
