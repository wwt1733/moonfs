# moonfs —— 纯 MoonBit 的只读文件系统镜像解析库

moonfs 是一个纯 MoonBit 的只读文件系统镜像解析库：直接解析镜像字节，不挂载、不依赖 C 库、不要 root。一期交付 NTFS 3.1 的完整读取（含 LZNT1 压缩、稀疏段、跨记录属性），二期 ext4。

- **参赛者**：王文挺｜联系方式见报名问卷（公开仓库不放手机号）
- **仓库**：GitHub <https://github.com/wwt1733/moonfs>｜GitLink <https://gitlink.org.cn/wwt1733/moonfs>（同步镜像，29 个提交，全部实质开发）
- **方向**：存储基础设施 / 文件系统解析｜**性质**：原创实现，依据公开规范编写，非移植（见末节）
- **本版针对 11/18 复审意见**：非驻留的 `$ATTRIBUTE_LIST` 已实现（含 `$MFT` 自身拆段），并补 `deep.bin` 与 `synth-mft-split.img` 两处代表性案例

## 一、为什么在 MoonBit 里做

能读 NTFS 的实现几乎都是 C：Linux 侧 `ntfs-3g`（GPL）与内核驱动，Windows 侧 `libfsntfs`。它们要么要求挂载（root / 管理员），要么必须链接原生 ABI——**结果是 WebAssembly 里读不了一块磁盘镜像**。不是没人想做，是这些实现的形态决定了它们进不了 wasm。

MoonBit 的 `preferred_target` 可以是 wasm，而 wasm 里没有可绑的 C 库——moonfs 补的正是这个位置：同一份源码在 native / js / wasm-gc 三个后端跑，这不是把 C 库翻译一遍。查重：mooncakes.io 全部 3794 个包中 `ntfs` / `ext4` 相关实现为 **0**；FAT 家族已有 `chenliyi-cly/moonfat`，本项目不做 FAT，改为经统一卷接口对接它。

## 二、通用性：三层可插拔

"通用"不靠支持多少种格式，靠分层——每层只依赖上一层的输出：

| 层 | 输入 → 输出 | 换的时候动哪里 |
| --- | --- | --- |
| 字节层 `@block` | 一段字节 → 越界即报错的只读视图 | 数据源换成文件 / 内存 / wasm 宿主内存，上层不动 |
| 定位层 `@partition` | 镜像 → MBR / GPT 分区表（GPT 双 CRC 校验）→ 卷起始偏移 | 裸卷传 0、分区内卷传 `start_lba`，同一份代码 |
| 结构层 `@ntfs` | `(Image, base_offset)` → 目录树与文件流 | 二期 ext4 只换这一层，前两层复用 |

这不是口号，两条路径都在 CI 里：`testdata/synth-ntfs.img` 是**裸卷**（引导扇区在偏移 0），`testdata/win-ntfs.img` 是**分区内卷**（MBR，起点 LBA 128），同一个 `Volume::open` 各跑一遍。一期只交付 NTFS，是为了让边界可验收——一种格式端到端读对，胜过多半种格式各读一半；二期 ext4 与 FAT 对接都落在这一层里。

## 三、预期使用场景

1. **浏览器端镜像浏览（核心）**：网页上传 `.img`，前端用 moonfs（wasm-gc）列出分区、目录与内容，全程不出本地。C 绑定方案在此不可行。
2. **数字取证**：打开 DD 镜像枚举文件、导出 MFT 时间戳做时间线，不挂载、不要写权限，可在只读介质上批量跑。
3. **CI 镜像内容校验**：构建完根文件系统后直接断言"没有多余调试文件、`/etc/shadow` 权限位正确"，不起容器、不挂 loop 设备。

## 四、一期交付范围

**NTFS 3.1**：Windows XP 起的默认版本，覆盖当前在用的全部 Windows。版本号读自 `$VOLUME_INFORMATION`；读到 3.0 / 1.2 卷时结构层仍可解析，但 `$Secure` 等后加元文件的语义不做承诺。

"解析文件系统"没有终点就没有验收标准，一期分三层收口：

| 层 | 终点 | 判据 |
| --- | --- | --- |
| 元数据 | 镜像字节 → 完整目录树 | 每条给出路径、逻辑大小、占用大小、时间戳、压缩/稀疏标志、MFT 记录号 |
| 内容 | 任意文件 → 正确字节流 | 常驻、多段、稀疏、LZNT1、尾部不足一压缩单元、跨记录合并六种情形，逐字节等于原文件 |
| 导出 | CLI 落盘 | `ls` 出目录树、`cat` 出内容、`export` 还原文件 |

**做**：MBR / GPT 定位；卷头几何；MFT 与 USA 修复；属性链与 `$ATTRIBUTE_LIST` 跨记录合并（列表自身常驻或非常驻均可）；runlist（有符号增量与稀疏段）；`$I30` B+ 树目录（区分 Win32 / DOS 命名空间）；常驻 / 多段 / 稀疏 / LZNT1 四种数据路径；CLI `info` `partitions` `ls` `cat` `export`。

**不做**：写入与日志重放；删除文件找回；EFS 解密（要用户证书私钥，离线解析拿不到，遇即报错且不吐密文）；ext4（二期）；挂载与内核集成。

## 五、含压缩文件镜像的预期行为

`testdata/synth-ntfs.img`（22 KiB，NTFS 3.1，根目录六个文件，`tools/make_test_image.py` 可重跑）：

| 文件 | 特征 | 逻辑 / 占用 | `moonfs cat` 预期 |
| --- | --- | --- | --- |
| `hello.txt` | 常驻未压缩 | 14 / 14 B | 14 字节原文 |
| `big.bin` | 非常驻跨 2 簇 | 1000 / 1024 B | 1000 字节，跨簇拼接正确 |
| `compressed.txt` | LZNT1，压缩单元 2 簇 | 1024 / 512 B | **解压后 1024 字节**，与压缩前逐字节一致 |
| `sparse.bin` | runlist 只有未分配段 | 512 / 0 B | 512 个零字节 |
| `split.bin` | `$DATA` 两段，分放两条 MFT 记录与不相邻簇 | 2000 / 2048 B | **2000 字节**，按 VCN 拼好 |
| `deep.bin` | 同上，且 `$ATTRIBUTE_LIST` 自己也搬到簇上（非常驻） | 2000 / 2048 B | **2000 字节**，列表先从簇上读出再合并 |

`ls /` 列出全部六个条目，压缩文件标 `compressed` 并同时给逻辑大小与占用大小；EFS 文件返回 `Encrypted(path=...)`、退出码非零、不输出密文；三个后端输出与退出码一致。这张表已进 CI：每次 push 都在 wasm-gc 下真正执行 `export` 并逐字节比对。

### 代表性案例：列表自己也要从簇上读

属性多到一条记录装不下时，NTFS 把多出来的部分放进扩展记录，用 `$ATTRIBUTE_LIST` 串起来；属性再多，列表本身也装不下记录，于是被搬到簇上。这里有个循环：读扩展记录要先有 MFT 的 runlist，而 runlist 由住在 MFT 里的属性描述。解法是——列表带着自己的 runlist，按普通数据属性读即可，不需要先打开 MFT。

两块专用镜像各钉住一半：

| 镜像 | 制造的结构 | 预期 | 处理错的后果 |
| --- | --- | --- | --- |
| `synth-ntfs.img` | `deep.bin`：两段 `$DATA` 分放记录 12 / 13，列表非常驻于 LCN 40 | `cat` 得 2000 字节 | 只并第一段，**静默少读一半** |
| `synth-mft-split.img` | `$MFT` 的 `$DATA` 拆两段（LCN 10..17 / 20..27），列表非常驻；根目录记录 5 与文件记录 6 都在第二段 | `ls /` 得 `after.bin`，`cat` 得 29 字节 | 只剩第一段，**根目录都读不出** |

两条断言都在 CI 里跑；把修复回退后它们会分别报 “MFT runs = 1” 和 “2 != 4”，不是靠肉眼确认。

### 真实 Windows 卷

只用自己写的合成镜像自证不算数——编码器与解码器可能共享同一个误解。所以另有一块 Windows 自己格式化的卷：`diskpart` 建固定 VHD → `format fs=ntfs` → `compact /c` 压缩，再截掉 VHD 尾部 footer（`testdata/win-ntfs.img`，24 MB，git 压缩后 182 KB，已入库）：

| 文件 | 写入内容 | 占用（`compact` / 本项目） | 导出 SHA-256 |
| --- | --- | --- | --- |
| `big.txt` | 204847 B，79 字节一行重复 | 28672 / 28672 B | 一致 |
| `mixed.bin` | 196608 B，前 64 KiB 确定字节 + 后 128 KiB 全零 | 12288 / 12288 B | 一致 |
| `plain.txt` / `small.txt` | 69 B / 4 B 常驻 | 69 / 69、4 / 4 B | 一致 |

`tests/e2e/windows_test.mbt` 在测试里重算这四个文件的内容再比对，CI 每次 push 都在跑真实 LZNT1 数据。这块卷也抓出了两个被合成镜像掩盖的错误：卷头 `clusters-per-index-buffer` 偏移读错（0x44 读成 0x41）、LZNT1 短语「长度位 / 距离位」的动态分栏被写死。两处已修，真实压缩块留作回归向量。

## 六、实现路径与验证

| 层 | 关键判断 | 错一步的后果 |
| --- | --- | --- |
| 字节 | 每次读前校验 `[offset, offset+n)` 落在缓冲区内 | 截断镜像被解析成"看起来合法"的残缺结构 |
| 定位 | `clusters_per_mft_record` 是**有符号**字节，负值表示 `2^-n`；GPT 先验 CRC 再用偏移 | 后面读 MFT 全部跑偏；CRC 不过的头部字段可指向镜像任意位置 |
| 结构 | USA 先修复；runlist 的 LCN 是**有符号增量**；目录索引项的文件引用是自己而非 `$FILE_NAME` 的父目录；压缩单元有"压完更大所以原样存储"与"整单元未分配"两个分支 | 跨扇区字段全错；簇号变天文数字；目录漏条目；把原文当 LZNT1 解并输出垃圾 |

**验证**：LZNT1 用固定向量单测（未压缩块、短语回溯、重叠复制、多块拼接、越界报错），其中一条取自真实 Windows 卷；合成镜像由脚本生成、评审可重跑；端到端断言在三个后端各跑一遍；CI 三道防呆——零测试即失败、CLI 出错返回非零、e2e 步骤必须真正比对内容。
